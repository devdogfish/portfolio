## Quick setup

1. Install PostHog in production only. Use anonymous events and disable session replay. Add explicit events for selected outcomes. Separate contact clicks from successful contact submissions and résumé clicks from confirmed downloads when the site can observe those outcomes. [Anonymous events](https://posthog.com/docs/data/anonymous-vs-identified-events), [Web analytics dashboard](https://posthog.com/docs/web-analytics/dashboard)
2. Use built-in reports for sessions, conversion goals, and retention. A return cohort measures a browser identifier that persists across sessions. Browser resets and other devices can split the same visitor. For actual foreground time, add one narrowly scoped event that records visible milliseconds per route, pausing on tab hide and flushing on route transitions or hide. Label it foreground time unless an idle cutoff also excludes unattended tabs. [PostHog dashboard](https://posthog.com/docs/web-analytics/dashboard), [Page Visibility API](https://developer.mozilla.org/en-US/blog/using-the-page-visibility-api/)
3. Have the private Quantself dashboard read bounded daily or weekly aggregates via a server-side PostHog Query API credential. Cache the results. Use a supported batch destination if Quantself needs its own durable raw archive or retention beyond one year. Keep visitor IDs out of public charts. [API limits](https://posthog.com/docs/api), [Batch export destinations](https://posthog.com/docs/data-pipelines/batch-exports), [Event retention](https://posthog.com/pricing)

Choose self-hosted Umami if keeping event records on your own infrastructure is required and operating a separate service is acceptable. Build a collector only if a requirement remains unmet by both.
